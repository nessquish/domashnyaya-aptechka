ЖУРНАЛ РАЗРАБОТКИ (DAILY SCRUM)
===============================

Короткий самоотчёт в начале каждого рабочего дня этапа «Реализация бизнес-логики
и UI» (дни 7-12): что сделано, что планируется, какие есть препятствия.
Записи вносятся по факту.

День 7
------

Что сделано вчера: утверждены ТЗ, ER-диаграмма и макеты в Figma; выбраны Python,
Qt (PySide6), SQLite, unittest, black и flake8; выбрана стратегия Feature Branch
Workflow.

План на сегодня: основа проекта, Git и база данных:
- создан репозиторий на GitHub, настроены black, flake8, pre-commit, .gitignore;
- структура слоёв: база, репозитории, сервисы, интерфейс (раздел 2 ТЗ), README;
- схема базы SQLite строго по ER-диаграмме из ТЗ, менеджер базы (Database
  Manager), все запросы с параметрами, без склейки строк;
- хэширование паролей (PBKDF2 с солью), тестовые данные;
- модульные тесты для всего перечисленного.
Работа ведётся в ветке feature/database, затем Pull Request в main.

Препятствия:
- из-за настоящего «тяжёлого» хэширования паролей тесты шли около 30 секунд.
  Решение: в тестах используется малое число повторений хэша.
- ошибки базы (повтор логина, нарушение связи) должны превращаться в понятные
  сообщения. Решение: свои классы ошибок с текстом для пользователя и именем
  поля, к которому относится ошибка.

День 8
------

Что сделано вчера: настройки проекта, схема БД по ER-диаграмме, менеджер базы,
хэширование паролей, тестовые данные, 32 теста; ветки main и feature/database
отправлены на GitHub, открыт Pull Request.

План на сегодня: бизнес-логика, часть 1 (чистый код, docstrings, CRUD):
- ветка feature/auth: проверка логина, почты и пароля, репозиторий пользователей,
  сервис авторизации (регистрация, вход по логину или почте, смена пароля);
- ветка feature/products: даты и форматирование, расчёт состояния товара
  (просрочен, скоро истекает, низкий остаток, норма), репозитории категорий,
  товаров и истории, сервис товаров (создание, чтение с поиском, фильтрами и
  сортировкой, изменение, удаление);
- docstrings у каждого модуля, класса и метода, тесты граничных условий.

Препятствия:
- встроенный в SQLite поиск LIKE не различает регистр только у латиницы, поэтому
  запрос «ибу» не находил «Ибупрофен». Решение: функция casefold, добавленная
  в соединение с базой.
- запись в историю и изменение данных должны быть одной операцией. Решение:
  сервис открывает одну транзакцию и передаёт соединение репозиториям.

День 9
------

Что сделано вчера: проверка ввода, репозиторий пользователей, авторизация, даты,
расчёт состояния товара, репозитории и сервис товаров с историей, 164 теста.
Ветки отправлены на GitHub, открыты Pull Request.

План на сегодня: бизнес-логика, часть 2 (остальные сущности ER-диаграммы):
- feature/notifications: модель и репозиторий уведомлений, сервис уведомлений,
  пересчёт при изменении товара;
- feature/shopping: список покупок (добавление вручную и из товара, отметка
  «куплено», удаление);
- feature/history-settings: просмотр и очистка истории, профиль и настройки
  пользователя;
- feature/dashboard: сводка для главного экрана;
- обзор кода и слияние веток после ревью.

Препятствия:
- уведомление должно появляться снова, если причина не устранена, но не терять
  отметку «прочитано». Решение: уведомления сверяются с состоянием товаров,
  новые создаются, устаревшие удаляются, у остальных обновляется текст.
- товар может иметь несколько состояний сразу. Решение: состояние считается
  чистой функцией от срока, остатка и числа дней предупреждения, в базе не
  хранится; в таблице показывается самое важное.

День 10
-------

Что сделано вчера: уведомления, список покупок, история, настройки и сводка
главной, 256 тестов; ветки отправлены на GitHub, открыты Pull Request.

План на сегодня: пользовательский интерфейс по макету Figma, часть 1:
- тема (светлая и тёмная палитры), шрифт Inter, рисование скруглений, теней и
  иконок кодом, без картинок макета;
- виджеты: кнопка, поле ввода, плашка, карточка, таблица, выпадающий список,
  диалоги внутри главного окна;
- окно приложения, экраны входа и регистрации: проверка почты и логина при вводе,
  вход по логину или почте, «Запомнить это устройство», тема операционной
  системы;
- интерфейс только вызывает сервисы и не обращается к базе.

Препятствия:
- Qt собирает файлы шрифта Inter в одно семейство и выбирает начертание по
  толщине; по имени «Inter Medium» шрифт не находился. Решение: тест проверяет
  семейство каждого стиля.
- выпадающие списки не должны «залипать» поверх других программ. Решение: список
  и диалоги это обычные виджеты внутри главного окна.
- ошибку в почте нужно показывать, но не мешать первому вводу. Решение: общая
  проверка полей: ошибка появляется, когда человек ушёл с поля или нажал кнопку,
  дальше поле проверяется на каждой букве.
- при верной почте и неверном пароле краснело и поле логина. Решение: сервис
  возвращает, какое поле неверно (login или password), интерфейс подсвечивает
  только его.

День 11
-------

Что сделано вчера: основа интерфейса (тема, шрифт, рисование, виджеты), окно
приложения, вход и регистрация, боковое меню.

План на сегодня: пользовательский интерфейс по макету Figma, часть 2:
- «Главная», «Моя аптечка» (поиск, фильтры, сортировка в два шага, выбор строк и
  массовые действия, страницы), форма и карточка товара;
- «Список покупок» с подсказками товаров, «Уведомления», «История» с очисткой;
- «Настройки»: внешний вид, уведомления, данные (экспорт, импорт, сброс),
  аккаунт, масштаб и размер текста;
- поиск по программе (Ctrl+F);
- гибкое окно до половины экрана, сворачиваемая боковая панель.

Препятствия:
- на русской раскладке не работали Ctrl+C, V и X. Решение: сочетания
  определяются по коду клавиши, а не по букве.
- копирование из поля пароля клало в буфер точки. Решение: для скрытых полей
  копируется настоящий текст.
- настоящий пароль в базе не хранится (только хэш), а в настройках его нужно
  показывать. Решение: пароль запоминается в памяти на время сеанса и на диск не
  пишется.
- настройки внешнего вида (размер текста, тема устройства, масштаб) не относятся
  к ER-диаграмме. Решение: отдельный файл предпочтений, схема базы не менялась.
- Qt запоминает масштаб при первом запуске. Решение: размер экрана узнаёт короткий
  отдельный процесс, а ручной масштаб применяется до создания окна.
- поиск не находил формы слова («витамины» и «Витамин D»). Решение: сравнение без
  учёта регистра, буквы «ё» и окончаний.

День 12
-------

Что сделано вчера: все экраны макета, тёмная тема, настройки, поиск, гибкое
окно и боковая панель.

План на сегодня: доводка, качество и документация:
- импорт и экспорт Excel и CSV, шаблон Excel на трёх листах (правила, «Моя
  аптечка», «Список покупок»), итог импорта с причиной для каждой пропущенной
  строки;
- чистка кода по принципам Clean Code (общие основы экранов, помощники дат и
  поиска), тесты: 768, покрытие кода 94 % (coverage.py), black и flake8 без
  замечаний;
- тестовый аккаунт со всеми видами данных (около 80 товаров, 85 позиций списка
  покупок, 50 уведомлений, 90 записей истории);
- вход и регистрация не зависят от масштаба пользователя, переключатель страниц
  показывает не больше пяти номеров;
- README: установка с .venv, руководство пользователя, устранение проблем;
  сборка Aptechka.exe (PyInstaller), очистка репозитория от лишнего.

Препятствия:
- выпадающие списки в Excel были пустыми: ссылка на другой лист не срабатывала.
  Решение: значения записаны прямо в проверку ячейки.
- «Добавлено 0 товаров»: количество в файле превышало допустимый миллион.
  Решение: программа показывает причину и номера строк, лимиты записаны на листе
  «Правила».
- масштаб Qt меняется только при запуске, а вход должен идти в своём масштабе.
  Решение: после входа и выхода программа перезапускается, вход без пароля идёт
  через запись, которая действует 2 минуты.
- окружение .venv весило 722 МБ из-за встроенного браузера в полном PySide6.
  Решение: PySide6-Essentials (288 МБ).
- в статистике языков GitHub появился JavaScript из-за одного файла скрипта.
  Решение: файл удалён.

Sprint Review (итог этапа, дни 7-12)
------------------------------------

Что удалось показать:
- приложение запускается из виртуального окружения и работает по макету: вход,
  регистрация, главная, аптечка, список покупок, уведомления, история, настройки,
  поиск по программе;
- база SQLite с полным набором операций: добавление, чтение с поиском и
  фильтрами, изменение, удаление (параметризованные запросы, без склейки строк);
- импорт и экспорт Excel и CSV, шаблон для заполнения;
- тестовый аккаунт со всеми видами данных;
- 768 автоматических тестов, покрытие 94 %, black и flake8 без замечаний;
- руководство пользователя и инструкция по запуску в README.

Что не удалось или осталось сделать:
- Pull Request с комментариями ревью нужно оформить и приложить к отчёту;
- у части методов (около сотни) нет строк документации;
- автоматическая проверка на GitHub Actions не настроена, исполняемый файл нужно
  собрать заново.

Sprint Retrospective
--------------------

Что прошло хорошо:
- слои база - репозитории - сервисы - интерфейс не пришлось менять при росте
  интерфейса, бизнес-логика проверялась тестами без окна;
- чистка кода и тесты на каждое изменение быстро находили поломки;
- Feature Branch Workflow и частые коммиты дали понятную историю.

Что можно улучшить:
- собирать шаблоны и тестовые данные скриптами с самого начала, чтобы не править
  файлы вручную;
- проводить Code Review через Pull Request после каждой ветки, а не в конце;
- писать docstrings сразу вместе с кодом, а не после;
- делать резервную копию файла перед любой его правкой;
- планировать день заранее и записывать план в этот журнал до начала работы.
